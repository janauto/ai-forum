# AI 研发中台 · 原型需求文档 v1.0

> [!quote] 北极星（继承自理念册子）
> **让研发知识可结构化沉淀、可检索复用、可追溯；AI 做记忆与镜子，人做判断与签字。** 凡偏离这一句的设计，都值得重新想一遍。

> [!note] 这份文档是什么
> 这是「原型」的需求说明，不是最终 PRD，也不是功能堆叠清单。它要回答三个问题：**我们要画哪些界面、每个界面解决哪条信息失真、AI 在每个界面上是"给事实"还是"下判断"**。评审通过后，下一步才是把它做成可点击的低保真原型。

---

## 0. 一页读懂（给老板/给团队的电梯陈述）

**一个平台，两个视角，共用一套数据地基。**

- **老板视角 = 决策驾驶舱**：把研发信息从「收集 → 呈现 → 辅助 → 决策」串成一条闭环。老板看到的是项目全景、历史工期/成本偏差、Build-vs-Buy 参照——**数据锚点，不是 AI 替他拍板**。
- **研发视角 = 辅助工作台**：本期原型的重点。**刻意弱化"收集"**（录入阻力压到 3 个字段），**优先把"呈现"做透**（历史案例/相似项目一键可查），**用户体验从"辅助"切入**（AI 当镜子，给事实不给判断）。按 **硬件 / 软件 / 结构 / ID** 四个岗位分类。

> [!important] 本期原型只验证一个核心假设（信条 15）
> **"研发愿意用、且 AI 能把对的历史信息推到对的人面前。"**
> 不验证自动决策、不验证 Agent 协作、不验证收集全流程——那些标记为「以后再说」。

---

## 1. 产品全景：两个视角 × 四个阶段

整个平台沿用「收集 → 呈现 → 辅助 → 决策」四个阶段。两个视角在四阶段上的**投入权重刻意不同**：

| 阶段 | 老板视角（决策驾驶舱） | 研发视角（辅助工作台 · 本期重点） |
|---|---|---|
| **收集** | 完整：信号原文第一时间结构化录入（信条 1） | **弱化**：仅在工作流中顺手记录，两段式 3 字段（信条 14） |
| **呈现** | 完整：项目全景 / 工期偏差 / 成本偏差仪表盘 | **优先做透**：历史案例检索、相似项目、失败库（信条 2/4） |
| **辅助** | AI 给事实锚点：历史工期、延期率、合作评分 | **体验起点**：AI 把相关历史推给对的岗位，给事实（信条 5/9） |
| **决策** | 完整：排期谈判数据支撑、Build-vs-Buy 参照（信条 9/10） | 不做决策，只把"已验证/预研/未知"三区诚实标出（信条 11） |

> [!tip] 一句话区分两个视角
> 老板视角回答**"我该把资源投到哪、该信谁的排期"**；研发视角回答**"这个活以前有人干过吗、踩过哪些坑、大概要多久"**。

**共用地基**：两个视角读写的是**同一套结构化知识库**。研发在工作台沉淀的每条案例/工期记录，自动成为老板驾驶舱的数据源——这正是信条 12「先把数据地基做扎实」的落地方式。

## 2. 设计准则（把 16 信条压成原型红线）

每画一个界面，过一遍这 7 条红线，违反就停下：

1. **AI 只陈述事实，禁用"建议/应该/风险高"**（信条 5/6）。文案模板：`历史上 N 个类似案例，平均 X / 实际 Y`，不写 `建议你…`。
2. **每条 AI 产出末尾必须有"由 [负责人] 确认"**，AI 提取物先进**待确认队列**才入库（信条 6）。
3. **录入只要 3 字段（场景 / 结果 / 原因）**；复用前才提示补全**约束条件**（信条 3/14）。
4. **失败与成功同字段、同收录、检索不降权**（信条 4）。
5. **检索结果必须落三区：已验证 / 预研 / 未知**；未知区敢说"这是空白"（信条 11）。
6. **每条记录有知识所有人；改动留 diff+人+时间；删除即归档不物理删除**（信条 16）。
7. **AI 的每个预测 append-only 存档，结果出来自动对比准确率**（信条 7/8）。

## 3. 研发辅助工作台（员工视角 · 本期原型重点）

### 3.1 岗位分类总览

四个岗位共用一套**骨架**（录入 / 检索 / 工期记录 / 待确认），只在**知识对象和 AI 呈现场景**上分化：

```
                ┌─────────────── 研发辅助工作台 ───────────────┐
   共性骨架 →   │  ① 知识录入(轻)  ② 知识检索(三区)             │
   (跨岗位)     │  ③ 工期偏差记录(锚点)  ④ 待确认队列            │
                └──────────────────────────────────────────────┘
                          │分化在「知识对象 + AI 呈现」
        ┌──────────┬──────────┬──────────┬──────────┐
        │  硬件     │  软件     │  结构     │   ID      │
        │ 选型/电路 │ 模块/协议 │ 结构/模具 │ 外观/CMF  │
        └──────────┴──────────┴──────────┴──────────┘
```

> [!note] 切入顺序（信条 13：从阻力最小处切）
> 原型默认先把**③ 工期偏差记录**作为"锚点功能"全岗位铺开——纯记录、零判断、当场可校正、对每个人都有即时价值。其余模块按岗位逐步展示更复杂的价值。

### 3.2 共性核心模块（四岗位通用）

#### 模块 ① 知识录入（两段式·轻到没借口不填）

- **第一段（录入即走，3 字段）**：`场景` / `结果（成功 or 失败）` / `原因`。失败案例与成功案例同一个入口、同一套字段（信条 4）。
- **第二段（被复用前才补全）**：当这条记录要进入检索结果/评估卡时，系统提示补 `约束条件`（信条 3——没有约束的经验复用比没经验更危险）、`知识所有人`、`关联项目`。
- 切信息失真节点（信条 1/2）：把"这个芯片不好用"这类纯主观，逼成 `场景+结果+原因` 的结构节点。
- 红线检查：✅ 把陈述变结构 ✅ 失败成功平等 ✅ 复用前补约束 ✅ 有知识所有人。

#### 模块 ② 知识检索（结果必落三区）

- 输入一个需求/问题，返回相关历史案例，**强制分三区呈现**（信条 11）：
  - **已验证区**：量产/验证过的方案，可直接复用。
  - **预研区**：试过但未量产，附当时结论与约束。
  - **未知区**：诚实标注"这是技术空白"，只给最接近的参照，不硬凑相似度百分比。
- AI 在这里只做**匹配与呈现**，不评分排序成"推荐度"。文案：`找到 3 条已验证 / 1 条预研 / 该方向无历史记录`。

#### 模块 ③ 工期偏差记录（★ 锚点功能，全岗位先上）

- 立项/接活时：**AI 与负责人各给一个估期，同时存档**（信条 8），append-only 不可改。
- 结项时：录入实际工期，系统**自动算偏差**并归档。
- 呈现：`同类复杂度历史均值 X 周 / 本次估 Y 周`——纯事实，谁都没法反驳（信条 5/9）。这就是给老板驾驶舱的"排期谈判数据"的数据源。
- 这是"零主观空间"的切入点，用来让最怀疑 AI 的人，靠"准确率自己说话"慢慢建立信任（信条 7）。

#### 模块 ④ 待确认队列

- AI 从会议纪要/文档里提取的待办、案例、字段，**一律先进队列**，人确认才入库（信条 6）。
- 每条带 `来源原文链接`，确认时可改可拒，留痕。

### 3.3 各岗位专属（知识对象 + AI 事实呈现场景）

> 下列字段/场景为 v1 假设，**待与各岗位负责人确认**（见第 6 节）。

#### 硬件 (Hardware)

| 维度 | 内容 |
|---|---|
| 知识对象 | 元器件选型/BOM、电路方案、功耗记录、EMC/信号完整性、打样调试记录 |
| 轻量3字段示例 | 场景：低功耗采集 / 结果：选 A 芯片实测达标 / 原因：B 芯片温漂超标 |
| 复用前补约束 | 采样率≤X、温度范围、供电方案、成本目标 |
| 典型失败库 | 芯片缺货/批次差异、layout 干扰、功耗超标、EMC 不过 |
| AI 事实呈现 | `这颗芯片历史上有 3 次缺货记录` / `类似功耗需求上次用 A 方案，实测功耗 Y` |

#### 软件 (Software)

| 维度 | 内容 |
|---|---|
| 知识对象 | 固件/驱动架构、可复用模块、协议栈、Bug 库、性能瓶颈记录 |
| 轻量3字段示例 | 场景：BLE 大数据量传输 / 结果：复用 X 模块通过 / 原因：自研协议时序 bug 反复 |
| 复用前补约束 | RAM/Flash 上限、实时性要求、功耗预算 |
| 典型失败库 | 内存泄漏、时序/并发 bug、协议兼容、OTA 失败 |
| AI 事实呈现 | `类似功能上次复用了 X 模块` / `这个协议历史调试平均用了 N 周` |

#### 结构 (Structure / Mechanical)

| 维度 | 内容 |
|---|---|
| 知识对象 | 结构方案、模具记录、装配工艺、材料、跌落/防水测试、公差 |
| 轻量3字段示例 | 场景：IP67 防水 / 结果：双道密封通过 / 原因：单道密封盐雾后渗水 |
| 复用前补约束 | 尺寸/重量上限、防护等级、成本、可制造性 |
| 典型失败库 | 装配干涉、模具缩水、强度不足、散热不达标 |
| AI 事实呈现 | `类似防水等级历史用方案 X，跌落测试通过率 Y` |

#### ID (Industrial Design / 工业设计)

| 维度 | 内容 |
|---|---|
| 知识对象 | 外观方案、CMF（颜色/材料/工艺）、人机交互、品牌一致性 |
| 轻量3字段示例 | 场景：磨砂金属质感 / 结果：阳极氧化达标 / 原因：上批喷涂色差被退 |
| 复用前补约束 | 品牌语言、成本、可制造性、与结构的边界 |
| 典型失败库 | 外观与结构冲突、量产色差、手感不符、工艺良率低 |
| AI 事实呈现 | `类似 CMF 历史量产良率 X` / `这种外观语言和内部结构的历史冲突记录` |

## 4. 老板决策驾驶舱（决策视角 · 全流程）

老板视角把四阶段全做，但 AI 始终在"见证者"位置（信条 5）。

| 层 | 界面/能力 | 对应信条 |
|---|---|---|
| **收集层** | 信号原文结构化录入（老板看到好产品 → 第一时间结构化，而非转述三道） | 1、2 |
| **呈现层** | 项目全景看板：在研项目、工期偏差、成本偏差、延期率趋势 | 2、9 |
| **辅助层** | 立项前自动输出「历史参考工期 + 风险点（事实型）+ 三区相似案例」 | 9、11 |
| **决策层** | ① 排期谈判：`同类均值 X 周，本次少了 Y 周` 数据锚点；② Build-vs-Buy 参照：历史成本偏差/延期率/方案商合作评分——**给数据，人来选**（不替老板拍板） | 9、10 |

> [!warning] 决策驾驶舱的红线
> 这里最容易越界成"AI 替老板决策"。所有输出必须是**可对比的历史事实 + 三区诚实标注**，决策卡末尾永远是「由 [决策人] 确认」。

## 5. 信息架构与原型页面清单

下一步要画的低保真页面（按视角分组）：

**研发工作台**
1. 工作台首页（按岗位进入：硬件/软件/结构/ID 切换）
2. 知识录入（两段式表单：3 字段 → 复用前补全）
3. 知识检索结果页（三区分栏：已验证 / 预研 / 未知）
4. 工期偏差记录页（双估期存档 + 偏差对比）
5. 待确认队列页（含来源原文）
6. 单条知识详情页（含 diff 历史、知识所有人）

**老板驾驶舱**
7. 项目全景看板
8. 立项辅助页（历史工期 + 三区相似案例 + 风险事实）
9. Build-vs-Buy 参照页
10. 信号录入页（收集层）

**通用**
11. AI 预测准确率公开页（信条 7：准确率自己说话）

## 6. 待确认问题（评审时请逐条拍板）

1. **岗位字段**：3.3 节四个岗位的知识对象/约束字段，是否贴合你们真实工作流？哪个岗位先做样板？
2. **锚点功能**：默认先全岗位铺「工期偏差记录」。你更想先上这个，还是先上「会议待办跟踪」？（理念册子两处都提到过）
3. **数据来源**：知识库初始数据从哪来——历史项目复盘文档导入，还是从零靠日常录入沉淀？
4. **老板视角的优先级**：本期原型是「研发工作台为主、驾驶舱画 2-3 个示意页」，还是两个视角都要画全？
5. **AI 边界的尺度**：MVP 是否严格执行"禁用建议/应该/风险高"？还是允许带置信度的参考（信条 7 的后一阶段）？
6. **岗位范围**：除了 硬件/软件/结构/ID，是否还要加「测试 / 项目管理 / 供应链」等？
